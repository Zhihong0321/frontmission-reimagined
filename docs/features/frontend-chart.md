# Feature note: frontend chart

Owns: `web/chart/` (`chart.html`, `game-bridge.js`, `ops.js`, `ops.css`,
`chart-tiles-worker.js`, `art/`, generated `world.js`), `web/index.html`, and the
smoke suite `tests/browser/`. Verify with `tools\verify-feature.ps1 -Feature browser`.

## What it is

The player view served at `/chart/`. `chart.html` is Keeper's Chart: the game map
(WASD + click pathfinding through Core). Every other screen is the ops shell —
`ops.js` + `ops.css`, an ERP-style workspace docked over the chart; a new screen is
one more `registerPage`/`registerTab` entry, never a new page. `game-bridge.js` talks
to `/api/state`, `/api/map`, `/api/command` and owns no rule. `chart-tiles-worker.js`
renders map tiles off the main thread.

## Key facts

- All serving is repository-local: the host mounts `web/chart/`, and `world.js` is
  generated in-repo from `data/` by `make-world.js` (provenance is pinned by
  `tools/verify-worldjs.ps1`). There is no sibling fallback.
- `web/archive/` (the old isometric ops console) and `web/chart/_ops-test.html` /
  `opstest.html` (testbench pages) are not the player view; do not revive or extend
  the archive.
- Classic scripts, original execution order — no ES modules; the load order in
  `chart.html` is part of the contract.
- The smoke suite (`tests/browser/smoke.test.js`) fails on console errors, failed
  scripts/workers, and asset 404s, asserts WORLD/MECHA/OPS initialize and a
  deterministic command advances state through the bridge.

## Invariants and gotchas

- The shell never computes a rule: if a number is not on a view model, add it in
  `ViewBuilder` first.
- The browser caches the scripts: bump the `?v=N` query in `chart.html` for every
  script you change, or you will debug stale code.
- The ops shell re-renders on every snapshot (including each travelling day); keep
  per-screen state in `S`, not the DOM.
- Generated bytes under `web/chart/` (world.js) are pinned; a mechanical frontend
  split must preserve execution order and classic-script semantics.
